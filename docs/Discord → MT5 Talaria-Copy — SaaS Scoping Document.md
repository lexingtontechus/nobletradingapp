# Discord → MT5 Talaria-Copy — SaaS Scoping Document

**Version:** 2.0 · **Date:** 2026-09-10 · **Status:** Draft for review
**v2.0 changes:** Rewritten to reuse the EXISTING talaria_claims token ecosystem instead of inventing new tables (`copy_tokens`, `signals`, `deliveries`, `ea_status`, `orders`) and new edge functions (`ea-handshake`, `ea-poll`, `ea-ack`, `ea-heartbeat`, `ea-bundle`, `dashboard-api`). Token issuance reuses `talaria-credentials-panel.jsx` + `/api/talaria-claim` → `talaria_claims` table → `talaria-check` edge function. Signal polling reuses `v_talaria_latest_signals` (already anon-readable). No new DB tables; no new edge functions for token management or signal delivery. S5 stays as-is (daisyUI + Tailwind per AGENTS.md). S6 is pure MQL5 client of Supabase REST.

---

## 1. Purpose

Define the systems, user journey, and build plan for a SaaS feature that lets existing subscribers automatically copy signals to their own MetaTrader 5 accounts via an EA that connects out to our backend. Signals are generated by our existing `noble-trader-fastapi-backend` (Lightning Studio jobs writing `nt_sweep_result`); entitlement comes from existing Helio/MoonPay subscriptions. No MT5 terminals or VPS hosting burden on us; trades execute in the customer's own terminal.

**Key properties:**

- **Signals are born structured.** Lightning Studio jobs write `nt_sweep_result` with full signal fields (signal, entry_price, stop_loss, take_profit, qualified, p_win, ev, kelly_f, etc.). No Discord scraping or parsing needed for the primary path.

- **We never hold broker credentials.** The EA holds only our revocable claim token (reused from the existing Talaria plugin ecosystem).

## 4. The User Journey — Exact Actions, Exact Systems

### Step 0 — Prerequisite (already true)
Valid Helio subscription → Discord channels work today. That same valid subscription is the Talaria-Copy entitlement. Nothing to click, nothing to buy.

### Step 1 — Get the EA bundle · S5: existing portal/dashboard
1. Customer logs into the **website (S1)** and opens `/portal` (or `/welcome` after payment).
2. The page checks subscription status server-side (via `/api/subscription-status` which queries `subscriptions` with `status IN [pending, active, grace]`).
3. If active/grace, the **TalariaCredentialsPanel** renders (already exists in `app/components/talaria-credentials-panel.jsx`). The customer clicks "Reveal credentials" → POST `/api/talaria-claim` mints a 32-byte hex token (SHA-256 hashed at rest in `talaria_claims`, returned only once).
4. The panel displays the token in a bash-like env file format: `TALARIA_CLAIM_TOKEN`, `TALARIA_PLAN`, `TALARIA_EXPIRES_AT`. Copy buttons + "Download .env" + "Mint new token" (revokes old) all work today.

### Step 2 — Install in MT5 · Customer's own terminal, ~5 minutes
1. Install MetaTrader 5 and log into their account.
2. In MT5: File → Open Data Folder → unzip the EA bundle (the MQL5 source + a `.env.talaria` file with the token) into the `MQL5/` folder.
3. Drag **OneTradeCopy** onto any chart. In the inputs dialog, set `EnableTrading = true` and their risk preferences (`RiskPercentPerTrade`, `MaxLotsPerOrder`, etc.). Click OK.
4. The EA reads the claim token from `token.txt` automatically and calls `talaria-check` over HTTPS. The edge function hashes the token, looks it up in `talaria_claims`, and re-checks the LIVE `subscriptions` row. Returns `{ ok: true, plan_slug, plan_uuid, sub_status, period_end, grace_end }` or `{ ok: false, error: "invalid_claim" | "revoked" | "expired" }`.
5. The chart shows `OneTradeCopy · CONNECTED · Acct #12345 · Plan: Precision Pro`.

> **How the token actually works (reused from existing infra):** the token is the customer's identity to our backend, validated by `talaria-check` on every request. The raw token is stored nowhere — only its SHA-256 hash in `talaria_claims`. `talaria-check` re-reads `subscriptions` on every call, so a lapsed subscription immediately stops signal delivery. Minting a new token (via "Mint new token" in the panel) revokes the previous one via the single-active-token policy.

### Step 3 — Watch the first trade · S6 executes, S5 monitors
Next entitled signal from Lightning Studio → `v_talaria_latest_signals` is updated → the customer's EA picks it up within the poll interval, computes their lot size from their EA inputs, maps the symbol to the broker's exact name, sends the order with SL/TP, and reports the fill back to the dashboard (via a lightweight ack to a Supabase table or just local state).

## 5. S4 — Signal Delivery (reuses existing infrastructure)

### 5.1 Signal data source
- **Production writes:** `noble-trader-fastapi-backend` Lightning Studio jobs write `nt_sweep_result` with all signal fields. The table is already queried by `v_talaria_latest_signals` (migration 0009 in this repo + migration 110/130 in the fastapi backend).
- **No new tables needed.** The existing schema has everything: `nt_sweep_result` (signals), `nt_symbol` + `v_talaria_symbols` (symbol roster + plan gating), `v_talaria_latest_signals` (latest qualified signal per symbol).

### 5.2 Signal query for the EA (gateway HTTPS — no Supabase material in the EA)

**Design lock:** the customer EA must NOT embed Supabase URL, anon key, or service key. A third-party file holds only the gateway URL + the claim token. All Supabase access stays inside one Edge Function.

- **`talaria-copy` Edge Function** (`supabase/functions/talaria-copy/index.ts`) is the only EA-facing surface.
- The EA `POST`s `{ token, action: "handshake" | "poll" }` to that single HTTPS URL.
- The function hashes the token → `talaria_claims`, re-reads the LIVE `subscriptions` row, computes `entitled` (`active` | `grace`), and:
  - **handshake** → `plan_slug`, `plan_uuid`, `sub_status`, plan symbol roster (`v_talaria_symbols.plan_ids` containment).
  - **poll** → only `qualified = true` rows from `v_talaria_latest_signals` for those symbols (same column contract as §5.4).
- Desktop plugin keeps using `talaria-check`; the EA uses `talaria-copy` (shared claim model, EA-shaped payload).

Why not EA → REST + anon key: key rotation or project move would force an EA redistribution, and the published anon key would be enough to scrape signals. The gateway keeps both internal.

### 5.3 How EAs receive signals — WebSocket push (Option A, 2026-09-29)

**Decision:** MQL5 can open WebSockets (raw `Socket*` + RFC 6455, or an async WinHTTP DLL such as `asyncwinhttpwebsockets.dll`). The EA joins the **same Supabase Realtime Phoenix channel** as the desktop plugin:

- URL: `wss://<host>/realtime/v1/websocket?apikey=<anon_publishable>&vsn=1.0.0`
- Topic: `realtime:signals.<plan_slug>` (from handshake — never client-derived)
- Frames: object JSON `{topic,event,payload,ref}` (same as `plugin.js`)

`talaria-copy` **handshake** returns `realtime_url`, `realtime_apikey`, `realtime_topic`, `realtime_vsn`. Claim token remains for identity/entitlement TTL; the anon key is the same public publishable key the plugin embeds.

**Fallback:** REST `action=poll` every `PollIntervalSec` (default 10 min) if WS is down or the WSS DLL is missing. Light sweeps still write ~every 15 min; push delivers when the sweep publishes.

**TLS note:** `Socket*` is raw TCP — production `wss://` requires the WinHTTP/WinINet WebSocket DLL (or equivalent). Pure MQL5 WS is possible only against `ws://` or with a TLS wrapper.

### 5.4 Canonical signal contract (the EA consumer)
The EA reads `v_talaria_latest_signals` which returns per-symbol rows:

| Column | Meaning |
|---|---|
| `symbol` | Canonical symbol (e.g., `XAUUSD`, `BTCUSD`) |
| `signal` | `buy` / `sell` / `neutral` |
| `entry_price` | Trade entry price |
| `stop_loss` | Stop loss price |
| `take_profit` | Take profit price |
| `qualified` | Boolean — signal passed all qualification gates |
| `p_win` | Blended probability of winning |
| `ev` | Expected value |
| `kelly_f` / `effective_kelly` | Kelly criterion (scaled) |
| `aggression` | `passive` / `mid` / `aggressive` |
| `sweep_timestamp` | When the signal was generated |
| `markov_p_up` / `markov_p_dn` | Regime probability from `nt_regime_log` |

## 7. S6 — The EA (MQL5), Detailed Specification

### 7.1 Files & identity
- **Source:** `eas/OneTradeCopy.mq5` — single file, MQL5 stdlib only, no external dependencies. Defaults: `eas/OneTradeCopy.set`.
- **Identity:** `MagicNumber` input (default `20260908`) isolates EA-managed positions. Order comment carries a truncated dedup key (`OTC:…`) derived from `symbol` + `sweep_timestamp`, mapping local tickets to the sweep that opened them. Processed UIDs persist in `otc_state.csv`.
- **Token identity:** reads the Talaria claim token from `MQL5\Files\otc_token.txt` (one line). Presents it only to the `talaria-copy` gateway over HTTPS. **No Supabase URL or keys in the EA or token file.**

### 7.2 Inputs (ALL risk configuration lives here — nothing on the platform)

| Input | Default | Purpose |
|---|---|---|
| `EnableTrading` | **false** | Master consent switch; chart shows "set true to trade" until flipped |
| `Mode` | `Shadow` | `Shadow` logs actions only; `Live` sends orders |
| `RiskPercentPerTrade` | 0.5 | % of account equity risked per signal |
| `MaxLotsPerOrder` | 1.0 | Hard clamp per order |
| `MaxOpenPositions` | 5 | EA refuses new signals beyond this |
| `SlippagePoints` | 20 | Max deviation for market orders |
| `EndpointURL` | preset | **Only** network surface: `…/functions/v1/talaria-copy` (HTTPS enforced) |
| `TokenFilePath` | `otc_token.txt` | Claim token file in `MQL5\Files` |
| `StateFilePath` | `otc_state.csv` | Processed signal UIDs (idempotency) |
| `MoveSLToBEAfterTP1` | false | Optional breakeven behavior after first partial |
| `MaxSignalAgeSec` | 300 | Skip stale signals on pickup |
| `PollIntervalSec` | 2 | Gateway poll interval |
| `TransportMode` | `rest_poll` | Reserved for a later realtime upgrade; v1 is gateway REST only |
| `MagicNumber` | `20260908` | Isolates EA-managed positions |
| `SymbolMap` | `""` | Optional `XAUUSD=XAUUSDm,…` broker name overrides |
| `HttpTimeoutMs` | 8000 | `WebRequest` timeout |
| `RequoteRetries` / `RequoteDelayMs` | 3 / 400 | Market-order retry budget |

### 7.3 Lifecycle

1. **OnInit** — read `otc_token.txt`; if missing/empty: chart comment + journal with the exact fix ("reveal credentials on the portal, save token to MQL5\Files"). Otherwise `POST action=handshake` to `talaria-copy`. Response yields `entitled`, `plan_slug`, `plan_uuid`, `sub_status`, symbol roster. Build the **symbol map** (override map + fuzzy match vs terminal symbols, e.g. `XAUUSD` → `XAUUSDm`). Start `OnTimer`.

2. **OnTimer (every `PollIntervalSec`)** — `POST action=poll`. Gateway returns only qualified, plan-scoped signals. Re-handshake every 5 minutes (or on failure) so a lapsed subscription stops delivery. Skip when `entitled` is false.

3. **Signal processing** — skip if UID already in `otc_state.csv`; map symbol; compute lots from EA inputs; `Shadow` journals only; `Live` sends `OrderSend` with SL/TP (fallback open-then-modify on invalid stops).

3. **Signal processing** — per signal: check `qualified = true`; map symbol; compute lot size from EA inputs; send `MqlTradeRequest`/`OrderSend` with SL + TP; log the outcome.

4. **OnDeinit** — persist state file (processed signal UIDs, open positions) so restarts never double-fire.

### 7.4 Lot sizing (computed locally, from the user's inputs)
```
risk_amount   = AccountEquity × RiskPercentPerTrade / 100
sl_points     = |entry − sl| / Point (+ spread buffer option)
value_per_pt  = SYMBOL_TRADE_TICK_VALUE adjusted by tick size for 1.0 lot
lots_raw      = risk_amount / (sl_points × value_per_pt)
lots          = round down to SYMBOL_VOLUME_STEP
clamp         [SYMBOL_VOLUME_MIN, min(SYMBOL_VOLUME_MAX, MaxLotsPerOrder)]
```
Worked example: $10,000 equity × 0.5% = $50 risk · XAUUSD SL distance 120 points · tick value $0.01/point/lot → ~0.41 lots → normalized 0.40.

### 7.5 Execution
- Market orders via `MqlTradeRequest`/`OrderSend` with SL **and** TP attached in the same request; if the broker rejects combined SL/TP, open then `TRADE_ACTION_SLTP` modify immediately after fill.
- Limit/stop entries when `action=open` carries a distinct entry price (check broker `SYMBOL_TRADE_STOPS_LEVEL` first).
- Requote/price-off → re-request up to 3 attempts within 2s, then log the failure to the journal.

### 7.6 Resilience & idempotency
- Processed-UID set (persisted) → a re-polled signal is ignored; the EA only processes new `sweep_timestamp` values.
- Transport failures fall back to retry with backoff; connection status shown on chart.
- Restart reconciliation: enumerate open positions with our magic number, rehydrate state from the persisted file, log mismatches.

### 7.7 Local controls
- Chart panel buttons (MQL5 objects): **Close All (EA trades)** — flattens only magic-number-tagged positions; **Pause/Resume copying**. Status line shows connection state, mode, open count.

## 9. Security Model

- **No broker passwords, ever.** The EA presents only the Talaria claim token to the `talaria-copy` gateway.
- **No service-role Supabase material in the customer EA.** Option A (2026-09-29) ships the **anon/publishable** key + Realtime URL for push (plugin parity). No project service key, no raw claim hash storage in the EA. The gateway (`talaria-copy`) remains the only service-role client.
- **Claim tokens are hashed at rest** (SHA-256 in `talaria_claims`). The raw token is returned exactly once at mint time and can never be recovered from the DB. The `TalariaCredentialsPanel` already implements "Reveal credentials" UX — the token is only fetched on demand.
- **Single-active-token policy:** minting a new token revokes the user's other live claims (both the JS-side revoke in `/api/talaria-claim` and the DB-level partial unique index `talaria_claims_one_active_per_user_idx`).
- **Entitlement enforced on every call.** `talaria-copy` (and `talaria-check`) re-read the LIVE `subscriptions` row — a valid token does NOT bypass a lapsed subscription. The EA refuses to trade unless `entitled == true`.
- **All transport HTTPS.** The EA refuses a non-`https://` `EndpointURL`.
- **Signals are plan-scoped server-side.** The gateway filters `v_talaria_latest_signals` to the claim plan's symbols and `qualified = true`. The EA cannot widen the roster.

## 12. Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Supabase REST rate limits | Anon-key REST polling at ~30 req/min is well within limits. Realtime broadcast (Phase 4+) reduces request volume entirely. |
| Customer PC asleep → missed signals | Staleness check on `sweep_timestamp`; EA skips stale signals on reconnect. Customer can use Plexytrade VPS for 24/7. |
| Symbol suffix/name drift | EA auto-map + `v_talaria_symbols.tradingview_symbol` mapping. Unmapped symbols logged in journal. |
| Helio webhook gaps (failed renewal, grace periods) | `talaria-check` re-reads `subscriptions` on every call — entitlement is always live. Grace period handled by `subscriptions.status`. |
| Broker retcodes / execution failures | EA maps retcodes → journal log entries. Dashboard shows connection status from last `talaria-check` call. |
| EA distribution piracy / token sharing | Per-user token is the license; single-active-token; "Mint new token" kills leakers. Bundle includes the token per-download. |
| Regulatory posture | Talaria-Copy of our own signals into the user's own account, user-configured risk: prominent risk disclaimers, no performance guarantees, T&Cs reviewed before launch. |

## 13. Assumptions & Open Questions

**Assumptions**
1. Helio webhooks can maintain `subscriptions` status (active/grace/expired) — already proven by the existing `helio-webhook` edge function.
2. Lightning Studio jobs write `nt_sweep_result` with all signal fields — already proven (migration 029 enriches the table).
3. `v_talaria_latest_signals` is anon-readable — confirmed by migration 112 (anon read-only grants) + migration 139 (webapp read grant).
4. `v_talaria_symbols` exposes `plan_ids` for plan-scoped filtering — confirmed by migration 0009.
5. MT5 only for v1 (MQL5); MT4 would need an MQL4 port — deferred.

**Open questions**
1. Which Helio plan tiers include Talaria-Copy? Both Signal Scout and Precision Pro could qualify, but the EA polls `v_talaria_latest_signals` filtered by plan symbols — Scout gets 10 symbols, Pro gets 20. Confirm the plan tier gating is via `v_talaria_symbols.plan_ids` alone (no separate subscription flag needed).
2. EA distribution: static link to GitHub release, or per-user ZIP with embedded token? v1 alpha can use a static MQL5 file + the customer pastes their token into `token.txt` manually (reusing the existing TalariaCredentialsPanel reveal UX). Per-user ZIP is a Phase 2 refinement.
3. Platform-side kill switch: keep it local-to-EA only (current design), or add a server-issued "flatten" command later? Trade-off: user autonomy vs. incident response.
4. Server-side trade logging: is local MQL5 state file sufficient for v1, or do we need a `ea_acknowledgements` table? The existing `talaria_claims.last_validated_at` already tracks heartbeats via `talaria-check`.
